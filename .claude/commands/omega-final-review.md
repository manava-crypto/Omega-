Run **Final Review** on: $ARGUMENTS

Final Review is the most important gate. Rejecting Task Design, a source document, the prompt or the golden ends the task; a verifier REJECT sends that verifier back for repair and the task continues. Shipping a wrong task and terminating a correct one are both failures, so the answers handed to the user must be right the first time and must not change when the user asks "are you sure?". Run it as a multi-agent orchestration with repeated rounds of checks, never as a single pass; every contested verdict is judged, and every task-ending or overturned verdict is confirmed by a second judge, before it is written.

1. Prepare the inputs in the scratchpad: unzip the package into its own new directory; save the pasted Final Review screen verbatim to a file; save any prior review notes to a file. Confirm the upload matches the screen (task_id, revision, deliverable paths, verifier names); on a mismatch, stop and say so in the first line.
2. Run the workflow: `Workflow({ scriptPath: ".claude/workflows/omega-final-review.js", args: { pack_dir, screen_file, prior_notes_file, scratch_dir, user_notes } })`. Invoking this command is the user's opt-in to that orchestration. Three agents read the package once, in parallel, into a shared evidence ledger (instruction clauses and planned anomalies with the sources; the golden recomputed; every verifier's text, demands and golden result); two independent reviews run from that ledger; only fields with a split, a REJECT or a suspected External QC-type defect go to judges, four fields per judge; a second judge confirms any task-ending REJECT, any verdict that overturns both reviewers and any change, and a third settles a split; one "are you sure?" pass covers the REJECTs and close calls; then verdict-locked template F answers and one Auto QC pre-check. Agents read the short brief in reference 11 and the ledger, not the whole rulebook. It returns `answers`, `changes`, `unsettled` and `qc_problems`. If it returns `stop`, report a mismatch to the user in the first line, or use the fallback when the inventory or reviews failed. If `unsettled` is not empty, re-run those fields through the fallback rounds before relaying anything; if `qc_problems` is not empty, fix them without changing a verdict.
3. If the Workflow tool is unavailable, run the same stages yourself with the Agent tool: one agent builds the ledger; two independent reviewers who never see each other's verdicts; one judge per contested field, a second for any task-ending REJECT, overturn or change and a third on a split; one challenge pass; the writer; the Auto QC pre-check. Never settle a split by vote, and point every agent at reference 11 and the ledger rather than the full rulebook.

Every brief carries the bar: a verifier is rejected only when (a) its rubric misstates a governing term, (b) a realistic submission is mis-graded, shown on a supplied output or a fully described submission under an accepted reading (a PASS condition the prompt never asks for, or a single accepted reading where the prompt and sources allow another, meets this), or (c) where verifier and golden disagree, the verifier is the one that is wrong. The golden is rejected only when it truly fails a sound verifier or recomputes wrong from source; a non-verifier artifact only for a defect a correct solver cannot work around that the sources, the authority order and the prompt do not resolve. Everything else is an optional line: stale figures that change no result, hypothetical overlap or bundling, reasonable placement or format readings the prompt supports, extractor observability (NOT VERIFIABLE plus escalation), weight or difficulty labels, mechanical source slips and planned difficulty.

While it runs, do nothing else: the workflow notifies you when it finishes, so never poll it, sleep or read its journal, and do not start your own review in parallel. When it returns, re-check yourself only the deciding fact of each REJECT and of each task-ending verdict (the workflow has already re-adjudicated any doubt its writer raised); if there is no REJECT, relay without re-deriving approvals. If a check fails, re-run that field's adjudication rather than editing the verdict. Relay the answers inline in screen order under C1–C8 in SKILL.md, without stripping fixes, with one lead line listing any verdict the rounds changed. If the user later challenges a verdict, re-test it against the same bar; a changed verdict states "changed because <new evidence>".
